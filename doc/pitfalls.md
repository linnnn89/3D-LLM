# 踩坑与失败记录 (Pitfalls & Failure Log)

## 一、这份文档用来干什么

只记**已经真实付出代价的失败**：调试很久找不到的错误、交付后被打回的修复、方向选错导致的白工。

每条记录的重点不是"怎么操作"，而是：

- **根因**是什么（尽量到源码/规范级别，别停在"差不多是这个"）
- **判据**是什么（怎么用一个可执行的检查确认就它，而不是猜）
- **教训**是什么（下次怎么在 5 分钟内提前发现，而不是再花两小时）

新增条目请追加到对应分节末尾，保持格式一致。踩坑细节如果已经在别处写清楚了，这里只留判据并链过去，不重复抄写。

## 二、3D 模型 / VRM

### 2.1 减面后模型整体变黑（第一轮）

- **模块**：`scripts/optimize_vrm.py` + gltfpack，一个高模 VRM（VRM 0.x）
- **现象**：105 万面 → 15.6 万面，体积 56MB → 8.5MB，加载不报错，但**模型全黑**，只剩描边
- **根因**：gltfpack 的 `filterStreams` 会按材质语义裁剪顶点属性，其中一条规则是 *"Normal data for unlit materials"*。VRM 0.x 由 UniVRM 导出的 glTF 材质**全部带 `KHR_materials_unlit`**（MToon 的实现细节记在 `extensions.VRM` 里，gltfpack 读不懂），于是 `NORMAL` 被整列删掉；材质却仍挂着 `normalTexture`，渲染时顶点法线取 (0,0,0)，`dot(N,L)=0`。`TEXCOORD_1` 同理，因"材质没用到"被删（实际使用者是 VRM 扩展）。
- **判据**：读 glTF JSON 统计属性覆盖——`NORMAL 0/37`、`TEXCOORD_1 0/37`，而 31 个材质仍带 `normalTexture`
- **修法**：gltfpack 加 `-kv`（keep source vertex attributes even if they aren't used）
- **教训**：这是 gltfpack 的**文档化行为**，不是 bug。凡是用通用 glTF 工具处理 VRM，都要先问一句"这个工具看得懂 VRM 扩展引用的资源吗"

### 2.2 加了 `-kv` 之后**仍然全黑**（第二轮，真正的黑因）

- **现象**：属性齐全（`NORMAL 37/37`、`TEXCOORD_1 18/18`）、骨骼映射 54/54、贴图索引全有效，**渲染依旧全黑**
- **根因**（两层叠加）：
  1. gltfpack 的**顶点量化**会把 UV 压进窄区间（实测 `u[0.019, 0.982]` → `u[0.001, 0.063]`，约 1/15.7），再按 `KHR_mesh_quantization` 规范在材质上写 `KHR_texture_transform: scale≈15.7` 做补偿。这一步本身**合规**。
  2. 但 **three-vrm 处理 VRM 0.x 时会整体重建材质**（`VRMMaterialsV0CompatPlugin._parseV0MToonProperties`）：它给所有贴图引用统一挂上 `extensions: {...oe}`，而 `oe` 只来自 `_portTextureTransform()`，即 VRM 扩展里的 `vectorProperties._MainTex`（ST 值）。**glTF 材质上原有的 `KHR_texture_transform` 完全不参与**，补偿被丢弃。
  - 结果：所有贴图都去采样纹理左上角极小区域 → 全黑。实测 `map.repeat` 与所有 `*UvTransform` 均为单位矩阵，坐实。
- **判据**：
  - 量化文件里 UV 的实际数值范围被压缩（读 accessor 数值，不是读元数据）
  - 用 three-vrm 在 Node 里加载后 dump 材质 uniform，`mapUvTransform` 等全是单位矩阵
- **修法**：gltfpack 加 `-noq`（完全禁用量化）。代价是体积从 9.4MB 回到 11.6MB，但减面目标（16.4 万面）不受影响
- **教训**：**这是结构性不兼容**——`VRM 0.x + gltfpack 量化 = UV 采样错位`，调参数救不回来。（VRM 1.0 路径不重建材质，无此问题）
- 详见 [`vrm_frontend/README.md` §5](../vrm_frontend/README.md)

### 2.3 验证方法本身翻车了两次（元教训，最贵的一条）

同一个问题连续交付两次失败，根因都不在代码，在**验证方法**：

- **第一次**：只验证了"属性**存在**"（`NORMAL 37/37`），没验证"属性**数值**对不对"→ 漏掉 UV 被压缩 → 用户实测仍全黑
- **第二次**：改用逐 `(mesh, primitive)` 下标做前后对比，结果大量误报。因为 gltfpack 会**重排/合并 primitive、去重顶点**，下标根本对不上
- **判据/正确做法**：
  - 对比要以**材质名**为锚点（gltfpack 保名不合并，`-km`），不能用下标
  - 简化会删顶点，所以 UV 判据是"**新范围 ⊆ 旧范围**"（越界量 < 0.02），不是逐点相等
  - **静态自检通过 ≠ 渲染正确**：交付前必须跑真实渲染（无头浏览器 + 截图 + 像素平均亮度），并在同一页面里放一个**基准模型**作对照——如果基准也黑，那是工具错了，不是模型

### 2.4 自检误报：把合法优化当成破坏

- **现象**：新加的"属性编码是否被改动"自检一上来就报错退出
- **根因**：`JOINTS_0` 从 `ushort` 变 `ubyte`、`WEIGHTS_0` 从 `float` 变**归一化** `ubyte`，都是 glTF 核心允许的正常优化，不影响外观
- **修法**：检查范围收窄到会改变外观的属性（`POSITION / NORMAL / TANGENT / TEXCOORD_* / COLOR_0`）
- **教训**：检查项要写清"我在防什么"，否则会把正常优化也拦下来，最后被当成噪音无视

### 2.5 贴图被回收导致加载即报错

- **现象**：`Cannot read properties of undefined (reading 'extensions')`，炸在 three.js 的 `GLTFTextureBasisUExtension.loadTexture` 里，极具迷惑性
- **根因**：gltfpack 只认 glTF 标准材质的纹理引用，`_SphereAdd`、`_OutlineWidthTexture` 这类**只被 VRM 扩展引用**的贴图被判为无人使用而删除，`textures` 数组变短，VRM 里记录的旧索引越界
- **修法**：`optimize_vrm.py` 把这类纹理按 `(source, sampler)` 匹配后**补回数组末尾**并重映射索引
- **教训**：VRM 的资源引用关系比 glTF 标准多一层，"数组长度变了"这种小事会引发看起来很远的报错

### 2.6 全局比例简化会无差别砍掉小网格

- **现象**：`eyes` 网格在 `-si 0.1` 下从 360 面掉到 28 面，五官糊掉
- **修法**：配合 `-se`（误差上限）使用——它让简化自适应，大网格砍得狠、小网格受保护
- **教训**：比例参数是全局的，细节部位要靠误差约束兜

## 三、前端与运行环境

### 3.1 "白模、没有五官"被误判成模型问题

- **现象**：喜多郁代渲染成白模，一度怀疑模型资产损坏
- **根因**：**渲染设置**问题——ACES 电影级色调映射压缩了浅色贴图对比度，叠加过强的总光照，把脸部和五官洗白；模型本身完好
- **教训**：模型"看起来不对"时，先排除渲染设置（色调映射 / 光照强度），再怀疑资产。MToon 是卡通着色，贴图颜色即最终风格，**不应套用电影级色调映射**

### 3.2 替换模型后页面仍加载旧文件

- **现象**：文件明明换了，视口里还是旧的
- **根因**：`CORSStaticFiles` 只对 `.js/.mjs/.html/.css` 下发 `Cache-Control: no-cache, must-revalidate`，**`.vrm` 不在名单里**，只有浏览器按 `Last-Modified` 算的启发式缓存兜着
- **修法**：名单加入 `.vrm`（2026-09-18）
- **教训**：静态资源的缓存策略要跟着"我们会频繁替换哪些文件"走；模型文件体积大，命中旧缓存时最难察觉

### 3.3 `localhost:12393` 拒绝连接

- **根因**：后端**不是常驻服务**，由 `app/launcher.py` 拉起、并随套壳窗口关闭而 terminate（仅当服务是本次启动器拉起时）
- **教训**：排查前先确认端口在不在监听，别把"服务没起"当成"服务坏了"

### 3.4 端口被僵死进程占着但服务是坏的

- **根因**：启动器只检查"端口是否被监听"，不检查服务是否健康，会连上僵死进程并打开空白/报错页面
- **处理**：见 [`app/README.md` §3.1](../app/README.md)

### 3.5 脚本施工时的小坑（零散但费时间）

- 工作区**外**的临时目录（如会话 scratchpad）写文件会被工具拒绝，脚本要落在项目内
- 中文输出下控制台默认 GBK，脚本里出现 `⊆` 这类字符会直接抛 `UnicodeEncodeError`；跑之前设 `PYTHONIOENCODING=utf-8` 或把输出重定向到文件再读

### 3.6 角色头部被裁掉：第一反应是"相机太近"，其实是模型世界尺寸不同

- **现象**：喜多郁代只看得见嘴和下巴，脑袋跑到画面外；由比滨结衣、雷电将军正常
- **走过的弯路**：第一反应是"相机太近了"，准备去调 `camera.position` / `controls.target` ——
  但三个角色**共用同一套相机参数**，改它会把本来正常的角色一起改坏
- **根因**：**各 VRM 的世界尺寸不同**。实测 head 骨世界高度：由比滨结衣 1.4111、
  喜多郁代 1.6014（1.135×）、雷电将军 1.5299（1.084×）。相机框的是世界坐标，
  个子高的角色头就出框了
- **判据**：
  - 量 head 骨的世界坐标，**不要只读 accessor 的 min/max 就下结论** —— 那只是网格局部空间，
    得先确认父节点没有缩放（本次实测三份模型缩放全为 1，才敢直接用）
  - 要区分「头骨」和「包围盒顶」：喜多的呆毛把包围盒顶到 1.9395，她的 head 骨却在 1.6014
  - 复现命令：控制台看 `[VRM] 尺寸归一化：head 骨 X → ×Y`，应满足 `head骨 × 系数 ≈ 1.4111`
- **修法**：加载后把 `vrm.scene` 缩放到统一头骨高度，**基准取原本表现正常的那个角色**，
  保证它逐像素不变 —— 见 [`vrm_frontend/README.md` §3.5](../vrm_frontend/README.md)
- **教训**：多个资产共用一套镜头参数时，**差异一定来自资产，而不是参数**。
  先量资产、再动参数；否则会出现"修好一个、弄坏两个"

- **现象**：爱蜜莉雅在前端可选，选中后无模型
- **根因**：`vrm-models/爱蜜莉雅/` 里误放的是**衣服文件**，不是模型本体

## 五、桌宠外壳（Electron / Windows 无框透明窗口）

> 背景：把浏览器套壳换成 Electron 无框透明窗口，让 3D 角色常驻桌面。
> 设计依据与逐项实测见 [`desktop_pet_ui_design_20260918.md`](desktop_pet_ui_design_20260918.md) §12，
> 实现细节见 [`../desktop/README.md`](../desktop/README.md)。

### 5.1 透明窗口的 `ready-to-show` 从不触发

- **现象**：窗口用 `show: false` 创建，等 `ready-to-show` 再 `show()` —— 结果窗口**永远不出现**，
  且没有任何报错，进程看起来一切正常
- **根因**：`transparent: true`（分层窗口）下该事件不触发。无法靠"多等一会"解决
- **判据**：日志里只有"窗口创建完成"，没有"已显示"；用 `did-finish-load` 打点立刻就能看到它触发
- **修法**：改在 `did-finish-load` 显示，另加一个 2.5s 定时兜底
- **教训**：透明窗口不能照抄常规窗口的显示时序。**"没报错"不等于"没出问题"**

### 5.2 `setResizable()` 运行时会永久破坏透明

- **现象**：想在运行时切换"能否拉伸"，调一次 `setResizable(true/false)` 之后，窗口**再也不会透明**，
  且不可逆
- **根因**：Windows 上 Electron 用「把 min/max 设为当前尺寸 + 移除 `WS_THICKFRAME`」实现
  `resizable:false`，而 `WS_THICKFRAME` 与分层窗口不兼容（electron#51094 / #51175 / #49173）
- **判据/正确做法**：
  - `resizable:false` 在**创建时**定死，之后**永不调用** `setResizable()`
  - 想程序化改尺寸，只要 `setMinimumSize(1,1)` + `setMaximumSize(0,0)` 解开 min/max 锁，
    `setSize`/`setBounds` 就能生效**且透明不丢**（实测，见设计文档 §12.1）
  - 即「保透明」与「能改尺寸」是**两件独立的事**，别把 `resizable` 当成开关
- **教训**：键盘/窗口样式类 API，凡是被 issue 标为"可能破坏渲染"的，先查"创建时设置"能不能满足，
  不要留到运行时切换

### 5.3 `setIgnoreMouseEvents(true, {forward:true})` 只转发 mouse **move**

- **现象**：窗口切成穿透后，鼠标在角色上点击会**直接穿到桌面**（选中了底下的图标），渲染器完全收不到 click
- **根因**：`forward: true` 只转发 mouse move，**不转发 click**
- **判据**：穿透状态下在角色上点一下，看桌面图标是否被选中
- **修法**：必须用 **hover 预切换** —— 每次 mousemove 做 raycast，命中角色就先取消穿透，
  等点击到达之后再切回去。不能等 click 再判断
- **教训**：这是"整窗生效"的 API，任何"局部可交互"的方案都要在**事件到达之前**完成状态切换

### 5.4 穿透的防死锁纪律：先证明 forward 可用，再开启穿透

- **现象（最危险的一种）**：如果 `forward` 转发在某台机器上失效，穿透后页面收不到任何 mousemove，
  raycast 永远不再跑 → 永远收不到"鼠标进入角色"的信号 → **角色再也点不动**
- **判据/正确做法**：窗口创建后**先整窗可交互**（不穿透），直到 preload 收到**第一个真实 `pointermove`**
  并上报给主进程，才允许进入穿透态
- **修法**：`main.js` 用 `pointerAlive` 门控；最坏情况只是退回旧行为（空白区不穿透），不会点死
- **教训**：凡是"状态切换后可能失去唯一反馈通道"的设计，都要有一个**先验证通道可用**的前置条件

### 5.5 穿透的初始状态没同步，启动后有一段"假死区"

- **现象**：刚启动约 15 秒内，角色上方的空白区域**点不穿**，直到鼠标先进一次角色再移开才恢复
- **根因**：主进程记的状态变量 `isInteractive` 初值与窗口**真实状态**不一致（窗口创建后实际可交互，
  变量却写的 `false`），而"未命中"分支里有一句 `if (!isInteractive) return`，于是**直接返回、
  永远不会切到穿透** —— 死锁在"可交互"那一侧
- **判据**：日志里 `已确认 mouse move 转发可用` 之后紧跟 `初始同步：…`。若中间有十几秒空白，
  就是初始同步缺失
- **修法**：首次上报时**不做宽限期，直接按真实命中状态同步一次**（`hoverSynced` 标志位）
- **教训**：主进程里镜像渲染器状态的变量，**初值必须等于窗口创建后的真实状态**。
  这类 bug 只在"启动后还没被事件纠正过"的窗口里出现，人肉测试很容易漏

### 5.6 第二条 `/client-ws` 连接会让上下文分叉、角色失声

- **现象**：独立的聊天窗如果自己连一条 WebSocket，AI 的回复文字能显示，但**角色不说话**
- **根因**：后端**每条** `/client-ws` 连接都会克隆一份 `ServiceContext`（各自的 `history_uid`），
  而 TTS 音频只推给**其中一条**连接
- **判据**：看后端"每条连接的 `client_uid`"是不是有两个；看 `chat_history/` 里是否出现两条并行的历史
- **修法**：**只允许角色窗口持有 WS**，其余窗口经 IPC 中继。本仓库用 preload 注入主世界脚本包装
  `window.WebSocket`，收发经 DOM `CustomEvent` 桥回隔离世界再走 IPC —— **不改 `vrm_frontend/` 源码**
- **教训**：多窗口客户端在"每连接一份会话状态"的服务端面前，**连接数就是会话数**。
  加窗口之前先确认"这个服务端允许多少条连接"

### 5.7 自动化测 UI 时的三个坐标/输入陷阱

用脚本模拟鼠标键盘验证穿透与输入时，连续踩到三次，全部会导致"看起来测试没生效"：

1. **PowerShell 默认不是 DPI 感知的**：`SystemInformation.VirtualScreen` 返回的是缩放后尺寸
   （本机 125% 缩放 → 报告 1536×864，实际 1920×1080），按物理坐标算出的落点**全部偏出目标窗口**。
   必须**先** `SetProcessDPIAware()` 再换算。另注意 Electron 的窗口尺寸是 **DIP**、
   UI Automation / Win32 报的是**物理像素**（本机 1 DIP = 1.25 px）
2. **`SetCursorPos` 不产生鼠标消息**，只移动光标；要做"模拟真实输入"必须用
   `mouse_event` / `SendInput`。而且**移动也必须走 `mouse_event(MOVE|ABSOLUTE)`** ——
   页面靠 `pointermove` 里的 raycast 决定穿透状态，只挪光标不产生 move 消息的话，
   点击会穿到下层去
3. **两次工具调用之间前台窗口会变**：`keybd_event` 总是打给**当前前台窗口**。
   "点击输入框"和"按回车"分两次脚本执行时，中间的焦点可能已经跑掉 ——
   字符进了输入框、回车却打到了别处，表现为"发了但没反应"。
   **点击 + 输入 + 回车必须在同一个脚本里连续完成**
- **教训**：模拟输入的脚本，要把它当成"一次原子的用户手势"来写，不要在中间插入任何其他操作

### 5.8 不要用 `.vbs` 做无控制台启动器（编码 + 静默挂起）

- **现象**：写了个 UTF-8 带中文的 `.vbs` 启动器，运行后什么都没发生
- **根因**：WSH 默认按 **ANSI** 解析 `.vbs`，UTF-8 中文被解成乱码后抛编译错误
  （`未结束的字符串常量`）；更麻烦的是 `wscript.exe` 报错会弹一个 **MsgBox**，它会**静默挂起** ——
  桌宠没启动，后台却留下一个看不见的模态窗口
- **修法/判据**：干脆不用脚本。`electron.exe` 本身是 **GUI 子系统**程序，直接启动**不会分配控制台**；
  一个纯 `.lnk` 就同时满足"无控制台"和"双击即用"，还没有编码问题
- **顺带纠正一个直觉**：**`conhost.exe` 存在 ≠ 有可见控制台窗口**。Node 用 `windowsHide: true` +
  管道 stdio 启动子进程时仍会创建一个 `conhost`，但它的 `MainWindowHandle = 0`。
  判断有没有可见控制台要**看窗口句柄，不能数进程**
- **教训**：交付"无窗口启动"时，验证方式是**枚举可见窗口**，不是"我没看到黑框"

### 5.9 `npm install electron` 的 postinstall 可能不下载二进制

- **现象**：`npm install` 正常结束，但 `npm start` 报找不到 electron
- **根因**：postinstall 有时不会下载二进制，`node_modules/electron/dist/` 缺失
- **判据**：看 `desktop/node_modules/electron/dist/electron.exe` 在不在
- **修法**：补跑 `node node_modules\electron\install.js`
- **教训**：Node 生态里"安装成功"只代表包解开了，**带二进制的包要额外确认二进制落地**

## 六、改动模型后的验收清单

替换 `vrm-models/` 里的模型前，逐项过一遍：
